# 0033. Shopify mapping and onboarding: several locations, packs and bundles, the import through the CSV job

**Status:** Accepted, 16 November 2026. Implements Phase 2 plan Section 5.14 (mapping and onboarding), decision D17, and PRD 8.5 (milestone I6). Builds on [ADR 0008](0008-shopify-sync.md), [ADR 0018](0018-imports-and-exports.md), and [ADR 0019](0019-packaging-labels-bundles.md).

**Summary:** Each Shopify location maps to a warehouse or a location (scopes may not overlap) and becomes the connection's allocation rule; each Shopify variant maps to a variant, a sales pack, or a bundle, and Shopify shows whole units of that; onboarding reads the store with a bulk operation, matches by SKU then barcode, and writes the new records as a CSV import the person previews; pictures stay on Shopify's CDN

## Decision

- **Locations (`shopify.locations.map`).** A connection maps any number of Shopify locations, each to one warehouse (every location in it) or one location (with its sub-locations). Two scopes may not contain each other (`scopes_overlap`): one unit shown at two Shopify locations could be sold twice. A Shopify location without a map is listed as unmapped and never synced. Each map has a receiving location (a location without children inside the scope, the first by path unless chosen) where the onboarding import receives Shopify's quantities. Saving the maps also writes the allocation rule of channel `shopify:<connection>` with the scopes in the order listed, so Shopify orders are reserved from what Shopify shows (D3); the merchant can reorder it in the stock settings.
- **Variants (`shopify.variants.map`).** A Shopify variant sells one unit of a variant, one sales pack of a variant, or one bundle (a variant with an active definition; a bundle takes no pack). Several Shopify variants may sell the same variant (the single and the 6-pack, which are separate items in Shopify), but two may not sell the same variant and pack: a unique index refuses it (`target_already_mapped`). Each map records how it was made (`sku`, `barcode`, `manual`, `onboarding`, `listing`); the onboarding import never replaces a map a person set.
- **What Shopify shows** (`core/src/shopify/targets.ts`). For each mapped item at each mapped Shopify location: `floor(available)` for a variant, `floor(available ÷ pack base quantity)` for a pack, and the smallest `floor(component available ÷ units per bundle)` for a bundle, summed over the scope with the shared `stock_positions` rule (ADR 0020). An archived variant, pack, or component shows zero. A stock change pushes every item mapped to the variant, its packs, and every bundle that uses it (`affectedLevels`); a map change pushes its items through the new outbox topic `shopify.levels.push`. A changed map clears the level's expected quantity, so the next push reads Shopify's quantity first and then sets Airstock's (ADR 0008).
- **Orders with packs and bundles.** A line of a pack reserves pack × quantity base units; a line of a bundle reserves its components. Both lower the expected quantity of the line's own Shopify item, because that is what Shopify lowered (A28: 72 units, 5 singles and one 6-pack sold, 61 left; the single shows 61 and the 6-pack 10).
- **Onboarding** (`shopify.onboarding.*`, the `shopify.onboarding.run` outbox topic, `packages/shopify/src/onboarding.ts`). One run per connection at a time. Each step is safe to repeat and says when to run again; a 30-minute sweep resumes runs whose message was lost.
  1. **Read.** A `bulkOperationRunQuery` reads products (title, status, description, options, pictures) and variants (SKU, barcode, price, options, picture, inventory item, available per location): four connections, two levels deep. Its ID is stored first, so a restarted job polls the same operation. The result is parsed (`__parentId` links children to parents) and stored in R2; every Shopify variant is also recorded in `shopify_catalog_variants`, where unmapped ones are listed.
  2. **Match.** Each Shopify variant matches by SKU (normalized as Airstock does), then by barcode (a variant's own, or a pack's: then it sells that pack). The rest are new, except archived Shopify products and a second variant matching the same record, which are skipped with a note. A new variant without a SKU takes its barcode, else `SHOPIFY-<id>`.
  3. **Preview.** New variants become a CSV (product key = the Shopify product, options, price, barcode, status, and `stock:<receiving location>` columns) uploaded and previewed as an ordinary import as the member who started it, so the duplicate check, field validation, and row errors are the import's own. The person sees the matches, the import's problem rows, and the Shopify locations whose quantities are not imported because they are not mapped.
  4. **Commit** runs `imports.commit` in the same transaction: the import job writes records and opening receipts (reason "opening stock") in chunks with checkpoints (ADR 0018). Matched variants keep their data and stock.
  5. **Finish.** When the import completes, the job maps every matched and created variant, 200 rows per transaction (`shopify.onboarding.finish`, an integration callback).
- **Quantities are Shopify's `available`**, never below zero, at mapped locations only. Orders placed before the connection already left `available` and stay Shopify's: their later fulfillments, cancellations, and returns are not followed.
- **Pictures by URL (D17).** A Shopify picture is a media record with `external_url` on `cdn.shopify.com`, no upload intent and no R2 object, its `sha256` the hash of the URL (one record per URL). The product's pictures link to it, the first one primary; a variant's own picture links to that variant. Thumbnails and display images are Shopify's CDN URL with a `width` parameter. Only products the import created get pictures; existing products keep theirs.
- **Access.** Mapping and onboarding need `connections.manage` (onboarding also `imports.run` and `catalog.write`) and a dashboard session; they are not MCP actions, because a person compares both catalogs. The `shopify.connections.list` output adds `locationMaps` and `unmappedLocations`; `shopify.mappings.set` stays for one location and SKU maps.
- **Rate limits.** The Admin client waits when Shopify answers `THROTTLED`, for the time its restore rate needs to refill the query's cost (at most 10 seconds, three times), and on HTTP 429 for `Retry-After`; then the job retries later.

## Why

- Mapping a warehouse covers a pilot with one warehouse and many shelves without mapping each shelf; refusing overlaps keeps every unit in at most one Shopify location.
- Writing new records through the CSV import reuses its preview, duplicate check, chunks, checkpoints, and opening receipts, which were measured on 10,000 rows (ADR 0018), instead of a second import path.
- Shopify already hosts the pictures; copying them would make originals, the largest storage cost per shop, a second time.

## Revisit when

A merchant needs one Airstock location shown at two Shopify locations, onboarding must import orders open at install, pictures must be edited in Airstock (then copy them), or Shopify changes the bulk operation format.

## Update, 16 November 2026: orders during the preview (PR #90)

Opening stock is Shopify's `available` at the catalog read, but variants were mapped only after a person committed the preview. An order placed in between (the preview can wait hours) was recorded as unmapped for good, and the first push wrote the opening stock over Shopify's lower number: the sold units were sold twice.

Maps made by the onboarding now carry `orders_from`, the onboarding's start (the read starts with it). A line recorded as unmapped of an order created since then is applied as if first seen once its variant is mapped: held, or, if Shopify already shipped it, taken out of stock (the fulfillments recorded meanwhile are applied to it). The finish step queues each such order as an order job and runs it right away; the job runner retries one that fails. The first push still processes orders and then reads Shopify (ADR 0008), and the line's record is dated at the order's creation, older than that read, so nothing is counted twice. Orders placed before the read stay Shopify's, as above; other maps (manual, by SKU, listings) have no `orders_from`. Evidence: F8 in `apps/worker/test/shopify-review-findings.test.ts` and the onboarding test in `apps/worker/test/shopify-order-sync-fixes.test.ts`.

A store installed again in the same shop keeps its maps: the new connection takes them over with its orders (ADR 0035).
